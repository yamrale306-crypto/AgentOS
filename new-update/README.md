# AgentOS — Update / Code Import Area

This folder is the **input/staging area** for new code generated by Gemini Studio or
other tools. It is a holding zone for incoming updates — it is **not** part of the
production application and must never be blindly imported into the build.

```
AgentOS/
├── frontend/
├── backend/
├── supabase/
└── new-update/          <-- you are here
    ├── README.md
    ├── UPDATE_MANIFEST.md
    ├── backups/          (safety snapshots, not committed)
    └── extracted-code/   (result of ZIP extraction, not committed)
```

---

## What this folder is for

Place **incoming generated changes** here before they are integrated:

- New features (new components, modules, utilities)
- UI redesigns / component replacements
- ZIP archives containing project changes
- Complete replacement folders (e.g. a new `frontend` variant)
- Documentation updates, migrations, config changes

## Where to paste things

| Item | Location |
|------|----------|
| A ZIP file | `new-update/` (e.g. `new-update/agentos-ui-update.zip`) |
| An extracted folder | `new-update/extracted-code/` |
| A raw feature/UI folder | `new-update/` (e.g. `new-update/feature/`, `new-update/ui-update/`) |
| Backup snapshots | `new-update/backups/` (created automatically) |

You may paste the ZIP directly into `new-update/`. The update tool extracts it into
`extracted-code/` during inspection — it never extracts over the live project.

## What should NOT be placed here

The update mechanism treats these as **dangerous** and will skip them:

- `.env`, `.env.local`, `.env.*` and any file containing secrets / credentials / tokens
- `node_modules/`
- `.git/`
- `.next/`, `dist/`, `build/`, `coverage/`, `out/`
- Lockfiles / generated artifacts that carry machine-specific paths where they can
  cause silent breakage without review
- Anything you do not actually want reviewed and mapped into the project

Never put real API keys, `.env` values, or auth tokens in this folder or in any
commit. Everything is treated as untrusted input.

## Rules of engagement

1. **Never overwrite the existing project just because something is in `new-update/`.**
2. Every update must go through the workflow: detect → inspect → compare → map →
   validate → integrate (see UPDATE_MANIFEST.md and the tool below).
3. Preserve existing functionality unless the incoming update **explicitly** requires
   changing it.
4. Pay special attention when an update touches: authentication, API routes, database
   logic, environment variables, task state management, research execution, source
   retrieval, security, and existing user flows.
5. Do **not** blindly replace `package.json`. Compare dependencies, add only what is
   genuinely required, and never downgrade/remove what the app depends on.
6. Do **not** commit `backups/` or `extracted-code/` into production.
7. The production build continues to use the existing `frontend/`, `backend/`, and
   `supabase/` structure. Nothing here is auto-imported into that structure.

## How to process an update

### Plan first — view what would change, without touching the project

```bash
python new-update/update_tool.py plan --source new-update
```

### Review the plan (additions / modifications / conflicts / dependencies)

The plan output uses this legend:

```
+ Added        new file to be created
~ Modified     existing file to be changed (diff shown)
- Removed      existing file to be deleted
! Conflict     both sides changed — human decision required
```

### Apply the (reviewed) update

```bash
python new-update/update_tool.py apply
```

`apply` only applies the changes listed in the plan, creates backups of anything it
modifies, and records the result in `UPDATE_MANIFEST.md`. It will not run silently —
conflicts are skipped and reported.

### Full automatic cycle (plan + apply)

```bash
python new-update/update_tool.py run --source new-update
```

### Inspect a ZIP without planning

```bash
python new-update/update_tool.py inspect --source new-update/agentos-ui-update.zip
```

## Gemini working instruction

Whenever new code is placed inside `new-update/`, run the full cycle:

1. Scan `new-update/`
2. Identify the update type (A: new feature, B: UI redesign, C: ZIP, D: full replacement)
3. Inspect every relevant file
4. Compare with existing AgentOS files
5. Determine dependencies
6. Identify conflicts
7. Create an integration plan
8. Apply only necessary changes
9. Preserve existing functionality
10. Run typecheck
11. Run lint if available
12. Run the production build
13. Verify affected user flows
14. Update `UPDATE_MANIFEST.md`
15. Report exactly what changed

The graphical "Updates" UI in the app mirrors this flow: drop a ZIP/folder, review the
detected additions/modifications/conflicts, then apply.
